# 企业日常经营系统设计规格

- 文档日期：2026-11-03
- 项目：ProjectRecorder
- 状态：已完成设计自检，等待用户复核
- 设计方法：Superpowers brainstorming + grilling + Frontend Design
- 实施方式：按四个阶段分别编写实施计划和交付，不一次性开发全部范围

---

## 1. 摘要

ProjectRecorder 目前已经覆盖项目、任务、工时、员工负荷、风险预测、知识库、社区、账号和企业身份治理。下一阶段的目标不是继续增加孤立功能，而是把它升级成公司的日常经营系统：

1. 工作从统一入口进入系统。
2. 执行过程有明确责任、验收和交付证据。
3. 管理决策有可追溯的数据依据。
4. 企业身份、权限、任免和经营结果相互匹配。
5. 普通员工默认使用简单、游戏化的执行界面。
6. 有权限的管理者按需进入高级经营决策界面。

整体实施优先级由用户确认为：

**治理与责任 → 管理决策 → 执行追踪 → 工作入口**

---

## 2. 产品原则

### 2.1 简单优先

普通员工打开软件后，先看到今天要做什么、下一步点哪里、能获得什么，不先看到项目表、预算表和风险矩阵。

### 2.2 高级能力渐进展开

复杂能力不删除。财务、毛利、能力缺口、审计、治理和跨项目分析放入高级模式，由权限控制入口。

### 2.3 每个结论必须有证据

任何风险、延期、成本异常、绩效判断或身份变更，都必须能下钻到原始任务、工时、审批、变更记录或投票记录。

### 2.4 权限必须由系统执行

客户端只负责显示。身份、股份、投票、积分、验收和审批结果由服务端校验，不能只靠隐藏按钮。

### 2.5 游戏化以真实成果为基础

不为点击、工时或任务数量直接发积分。游戏化奖励经过验收的成果、协作和知识贡献。

### 2.6 治理优先于效率

日常操作可以快，但治理、股份、重大任免和高风险权限必须留出正式表决和审计链路。

---

## 3. 非目标

以下内容不在本次优化范围内：

- 不把系统做成完整工资、社保或财务记账软件。
- 不让游戏积分直接决定工资、晋升或劳动关系结果。
- 第一版不接微信机器人，先支持粘贴和转发。
- 不用公开排行榜替代正式绩效管理。
- 不允许知识星球作为合同、薪酬、密钥和客户隐私的存储位置。
- 不为每个功能单独复制一套数据，简单模式和高级模式共享同一底层数据。

## 4. 用户与模式

### 4.1 简单模式

默认面向所有成员。界面围绕个人今天的工作展开，包含：

- 今天的任务和团队任务。
- 计时或手工工时。
- 当前积分、连续完成和奖励资格。
- 可解锁的知识内容。
- 个人历史、积分明细和已解锁内容。

简单模式不展示：

- 全公司预算和毛利。
- 跨项目风险矩阵。
- 全员绩效对比。
- 股份、投票规则和董事会记录。
- 无权限的人事或财务数据。

### 4.2 高级模式

只对拥有任一管理、财务、审计或治理权限的身份显示入口。默认首页为“经营决策中心”，不是项目列表。

高级模式包含：

- 今日决策队列。
- 项目、人员、财务、审批和治理下钻。
- 风险证据和影响分析。
- 统一审批收件箱。
- 能力缺口与资源冲突。
- 身份、股份、董事会和股东会。
- 审计记录。

### 4.3 模式记忆

系统记住每位用户上次选择的模式。权限被撤销后，如果用户已失去高级模式资格，下次登录自动回到简单模式。

## 5. 实施路线

### 阶段一：治理与权限

- 可复制的身份模板。
- 身份模板版本、权限四维配置和审计。
- 股东会与董事会分离。
- 普通事项和重大事项表决。
- 股东按股份权重投票。
- 有限积分池、董事会审批、董事长发放。
- 简单模式和高级模式框架。
- 游戏化视觉和积分展示。

### 阶段二：管理决策

- 经营决策中心。
- 统一审批收件箱。
- 项目合同、回款、成本和毛利口径。
- 工时经营维度。
- 人员技能、能力和未来 2～4 周资源缺口。
- 可执行风险预警闭环。
- 多维绩效证据。

### 阶段三：执行追踪

- 验收标准、交付证据和验收人。
- 任务依赖、跨部门交接和阻塞影响。
- 需求变更申请与工期、成本、资源影响分析。
- 执行记录与项目经营结果联动。

### 阶段四：工作入口

- 电脑和手机快速记录。
- 公开需求表单和二维码。
- 邮件转发入口。
- 待分诊队列、负责人和 SLA。
- 可解释优先级评分。
- 重复需求检测与合并。
- 外部状态通知和内部备注隔离。
- 需求转项目、任务或售前支持。

## 6. 身份系统

### 6.1 身份数量

身份模板数量不设上限，企业可以任意增加、复制和修改。

### 6.2 创建方式

新增身份默认采用：

1. 选择一个现有身份模板。
2. 复制其权限。
3. 逐项修改。
4. 保存为新版本。
5. 由有权限的人任命给成员。

### 6.3 身份管理员

- 股东会投票任免一名身份管理员。
- 同一时间只保留一个主要身份管理员，可有临时代理但必须有失效时间。
- 企业所有者负责初始化，之后不能单独绕过股东会修改治理权限。
- 身份管理员可修改普通经营权限。
- 身份管理员不能修改自己的身份。
- 身份管理员不能授予自己没有的权限。
- 身份管理员不能单独授予或修改治理、股份、全公司财务、全公司数据导出和身份管理权限。
- 高风险权限变更必须进入股东会表决。

### 6.4 身份模板版本

- 每次修改生成新版本，旧版本归档。
- 正在被使用的模板不能直接删除，只能停用并迁移。
- 必须先把持有者迁移到其他身份，才能归档。
- 模板修改立即影响所有当前持有者。
- 权限收紧立即生效。
- 权限增加从管理员设置的生效时间开始。
- 所有受影响成员收到站内通知。
- 已归档版本和迁移记录不可删除。

### 6.5 一人多身份

- 每位成员有一个主身份。
- 允许同时拥有多个兼任身份。
- 兼任身份必须设置生效时间和失效时间。
- 权限通常取并集。
- 财务、人事、治理等高风险权限不能因为兼任自动叠加，必须通过独立的重大事项表决。
- 临时兼任最长 7 天，可由 CEO 或企业所有者在自身权限范围内设置。
- 超过 7 天必须转为正式任免提案。
- 临时兼任必须填写原因并写入审计。
- 高风险权限不能通过临时代理授予。

## 7. 权限模型

权限不只保存为模块开关，而是四维结构：

| 维度 | 含义 | 示例 |
|---|---|---|
| 功能 | 可执行的操作 | 查看、编辑、审批、导出、管理 |
| 数据范围 | 可以操作的数据边界 | 本人、小组、部门、全公司 |
| 限制条件 | 业务约束 | 金额上限、风险等级、项目类型、客户类型 |
| 时间与委托 | 有效期和代理关系 | 2026-11-01 至 2026-11-07，代理部门负责人 |

### 7.1 权限示例

- 研发经理查看本部门项目，修改本部门任务，不可导出全公司数据。
- 财务查看全公司合同和成本，审批单笔不超过 5 万元。
- 项目经理管理指定项目，不查看其他部门人员薪酬。
- 董事长查看治理全量信息，但发放积分仍受董事会批准额度限制。

### 7.2 权限冲突

- 默认采用“显式授予才允许”。
- 高风险权限不会被普通权限并集自动提升。
- 权限撤销优先于兼任角色授予。
- 任何拒绝和越权尝试写入安全审计。

## 8. 股东会与董事会

### 8.1 股东会

- 由持股人组成。
- 按股份权重表决。
- 普通事项：50% 股份出席门槛，有效赞成股份超过 50%，默认投票期 3 天。
- 重大事项：全体股份的 2/3 以上赞成，默认投票期 5 天。
- 当事人可以参加涉及自己的投票，但必须披露利益关系。
- 投票明细仅对股东、监事、审计身份开放。
- 提案发起时锁定股份快照。
- 投票期间禁止股份调整和新股东加入。
- 计票、审计和展示使用同一份股份快照。

### 8.2 重大事项

- 董事长、董事、监事、CEO、身份管理员和财务负责人任免。
- 股份调整、增资、减资和投票规则修改。
- 企业所有权、管理者权限和治理权限变更。
- 超过公司年度预算 10% 或单笔重大金额的支出。
- 全公司数据导出、批量删除和公司注销。
- 股东会预先列入重大事项清单的其他内容。

### 8.3 普通任免

普通部门经理、项目经理、组长、岗位权限和非重大身份调整采用普通事项规则。

### 8.4 股份调整

- 首次系统初始化自动生成 100% 初始股份。
- 初始化完成后，所有股份调整必须进入股东会。
- 股份调整要求全体股份的 2/3 以上赞成。
- 企业所有者不能单独修改股份。

### 8.5 董事会

- 董事会成员由股东会选举。
- 一名董事一票。
- 超过半数董事出席方可表决。
- 普通董事会事项由出席董事过半数赞成。
- 董事长负责执行，不拥有额外一票。
- 小公司允许同一人兼任股东、董事和董事长，但系统中保留不同身份和表决记录。

### 8.6 董事会职责

- 按季度批准积分池总量和未发额度结转规则。
- 批准积分分配原则和单次发放上限。
- 监督经营和重大风险。
- 对董事长发放记录进行审计。
- 可冻结剩余额度或发起纠错，但不能修改已发放记录。

## 9. 积分与知识星球

### 9.1 积分发行

- 积分由董事会按季度批准有限额度。
- 未发放额度默认不自动结转，季度结束后作废；董事会可以在下一季度决议中明确批准结转。
- 董事长只能在批准额度内发放。
- 董事长不能给自己发积分。
- 用户不能手工给自己加分。
- 每笔积分必须关联可验证的交付、协作、知识贡献或其他奖励依据。
- 同一成果不能重复计分。
- 不可超过董事会批准的单次上限。
- 发放前检查剩余额度。
- 积分发放后永久有效。
- 积分不直接决定工资或晋升。
- 积分可以作为奖励兑换、知识解锁和成长等级的资格。

### 9.2 游戏化行为

奖励依据包括：

- 按时交付。
- 一次验收通过。
- 解决阻塞。
- 帮助他人。
- 沉淀可复用知识。
- 团队目标达成。

不直接奖励：

- 工时长度。
- 点击次数。
- 任务拆得足够小。
- 重复低价值操作。
- 自己发布内容后自己领取积分。

### 9.3 积分透明度

- 成员查看自己的积分余额、发放人、原因和时间。
- 董事会、董事长和审计身份查看完整台账。
- 普通成员默认只查看团队汇总。
- 个人具体明细不默认公开。
- 排行榜必须自愿参与，不展示个人低分排名。

### 9.4 知识解锁

- 可选知识内容可以消耗积分解锁。
- 解锁一次后永久访问。
- 内容更新不重复扣分。
- 内容下架后保留只读访问。
- 课程班或活动可以设置有效期。
- 制度、安全、合规、岗位必读和紧急操作内容永久免费。

### 9.5 知识内容边界

知识星球用于公开或团队共享知识，不保存：

- 密码和密钥。
- 身份证号、银行卡号和完整客户隐私。
- 薪酬和处分记录。
- 完整合同和治理投票细节。

发布时执行敏感内容检测：

- 高风险内容默认阻止。
- 中风险内容要求二次确认。
- 敏感业务内容引导进入有权限控制的高级模块。

## 10. 简单模式体验

### 10.1 每日首页

只保留四个区域：

1. 今天的任务。
2. 进行中的计时或工时。
3. 当前积分与连续完成。
4. 可解锁或兑换的内容。

任务卡只显示标题、截止时间、验收标准和一个主按钮。

### 10.2 信息架构

```text
┌ 今天 · 周三                 积分 860 ┐
│ 今日完成 3/5       连续完成 7 天       │
│                                      │
│ ● 09:30  接口联调          [开始]     │
│ │        验收：双方接口通过             │
│ │        完成可获奖励资格               │
│ │                                    │
│ ● 11:00  修复登录提示       [继续]     │
│ │        剩余 1 小时                  │
│ │                                    │
│ ○ 16:00  团队任务 3/4       [查看]     │
│                                      │
│ 可解锁：故障排查案例集 · 还差 140 积分  │
└──────────────────────────────────────┘
```

### 10.3 交互规则

- 默认进入简单模式。
- 使用单手可触达的主按钮。
- 页面不出现财务表格。
- 奖励以印章、成长轨迹和额度刻度表达。
- 不使用金币、礼花、抽奖机等儿童游戏视觉。
- 复杂操作通过渐进展开，不在一开始显示所有字段。

## 11. 高级模式体验

### 11.1 默认首页

高级模式默认进入“经营决策中心”，先展示需要管理者处理的事项，而不是项目列表。

### 11.2 信息架构

```text
┌ 需立即处理 3 项 ──────────────────────┐
│ 延期风险 · 回款异常 · 身份任免          │
├──────────────┬───────────────────────┤
│ 决策队列 38%  │ 证据与影响 62%          │
│              │                       │
│ 智慧园区延期  │ 为什么判断会延期          │
│ 研发人力冲突  │ 下游任务、工时、责任人      │
│ 采购审批超时  │ 建议动作与影响金额          │
│              │ [分派] [批准] [退回]       │
└──────────────┴───────────────────────┘
```

### 11.3 每日必须回答的问题

1. 哪些项目会延期。
2. 谁超负荷或闲置。
3. 哪些审批卡住交付。
4. 哪些项目预算、毛利或回款异常。
5. 今天必须由管理者拍板的决定。

---

## 12. 管理决策能力

### 12.1 风险闭环

每条预警包含：

- 结论。
- 证据链。
- 建议动作。
- 责任人。
- 截止时间。
- 影响金额或交付影响。

管理者可以：

- 确认。
- 分派。
- 延期并填写原因。
- 标记为解决。

系统必须持续验证，不能仅靠手动关闭风险。

### 12.2 统一审批收件箱

集中展示：

- 请假。
- 工时。
- 费用。
- 采购。
- 奖励。
- 任务延期。
- 身份任免。

按交付影响、金额和等待时间排序。

审批动作：

- 批准。
- 拒绝。
- 退回补充。
- 转交。

### 12.3 项目经营口径

每个项目增加：

- 合同额。
- 已开票。
- 已回款。
- 应付和已付外包。
- 人力成本。
- 预计完工成本。
- 预计毛利。

首页同时显示账面进度和经营结果。逾期未回款自动预警。

### 12.4 工时经营维度

工时增加：

- 可计费或不可计费。
- 正常或加班。
- 项目、售前或内部。
- 返工或等待。
- 出差。

常用标签自动带默认值，避免增加过多录入负担。

### 12.5 人员能力

成员维护：

- 技能。
- 等级。
- 证书。
- 可用时间。

分配任务时检查：

- 技能匹配。
- 请假。
- 已有承诺。
- 关键资源冲突。

驾驶舱显示未来 2～4 周能力缺口。

### 12.6 绩效

绩效记录包含：

- 交付准时率。
- 验收一次通过率。
- 返工。
- 客户和协作评价。
- 复杂度。
- 经营贡献。

工时只作为产能参考，不直接等于绩效。员工可以查看依据并提交说明，最终由有权限的管理身份复核。游戏积分不直接决定绩效、工资或晋升。

---

## 13. 执行追踪能力

### 13.1 验收标准

每个可交付任务必须有：

- 验收标准。
- 交付物或证据。
- 验收人。
- 完成定义。

任务状态包括：

- 待验收。
- 返工。
- 已验收。

负责人不能单独把任务标记为最终完成。

### 13.2 依赖与交接

任务支持：

- 前后置依赖。
- 交接物。
- 交接确认。
- 阻塞原因。

上游延期时，系统自动计算受影响的下游任务、项目日期和责任人，并把交接待办推给接收方。

### 13.3 变更控制

新增变更申请，包含：

- 变更内容。
- 原因。
- 紧急程度。
- 对工期、预算、毛利和关键资源的影响。

未经批准的变更不能直接覆盖原计划。

---

## 14. 工作入口

### 14.1 第一版入口

- 电脑和手机快速记录。
- 公开需求表单和二维码。
- 邮件转发到专用地址。
- 微信内容先通过粘贴或转发进入。

### 14.2 需求类型

- 客户需求。
- 销售机会。
- 内部改进。
- 故障。
- 临时事项。

### 14.3 分诊

企业指定需求协调员身份：

- 故障：2 小时内响应。
- 客户需求：1 个工作日内响应。
- 内部改进：3 个工作日内响应。
- 超时未分诊自动升级给部门负责人或 CEO。
- 分诊结果进入管理驾驶舱待办队列。

### 14.4 优先级

可解释评分：

- 业务价值加分。
- 紧急程度加分。
- 风险加分。
- 依赖关系加分。
- 投入成本和机会成本减分。

系统展示每一项分值来源。管理者可以覆盖排序，但必须填写理由。紧急故障可以走快速通道。

### 14.5 重复检测

- 提交时提示相似需求。
- 支持合并、关联或标记为独立需求。
- 合并后保留全部来源、提出人和沟通记录。
- 原始记录不能直接删除。

### 14.6 对外表单安全

- 外部提交者只能查看自己的申请编号和状态。
- 不暴露内部项目、客户和员工信息。
- 启用限流、验证码或邮箱验证。
- 限制附件类型和大小。
- 提交后只进入待分诊区。

### 14.7 外部沟通

- 自动发送受理确认和预计响应时间。
- 状态变化自动通知提交人。
- 外部可见进度和内部备注分离。
- 内部备注不会泄露。
- 所有回复归档到同一条需求记录。

### 14.8 转入执行

分诊结果可以直接转为：

- 项目。
- 任务。
- 售前支持。

保留需求来源、提出人、验收标准、附件和状态变化。一个需求可以拆成多个执行任务，但只能有一个主责任人和一个最终验收结论。

## 15. 审计与安全

### 15.1 审计可见性

- 股东、监事和审计身份查看全量治理与经营审计。
- 普通成员查看与自己有关的任免和权限变更。
- 审计记录不可删除、不可覆盖。
- 涉及股份、投票、权限、积分和验收的记录必须保存版本和操作者。

### 15.2 数据隔离

- 薪酬与处分只对 HR、指定管理者和本人开放。
- 合同、成本和毛利只对财务及授权管理者开放。
- 治理投票明细只对股东、监事和审计开放。
- 批量导出需要专门权限并写入审计。
- 知识星球禁止保存密码、密钥和完整客户隐私。

### 15.3 服务端校验

- 身份、股份、投票、积分、验收和审批都通过服务端 RPC 或受策略保护的操作执行。
- 客户端不能直接修改治理表和积分台账。
- 越权尝试写入安全审计。
- 高风险操作要求二次确认。

## 16. 通知

实时通知：

- 故障。
- 安全事件。
- 重大审批。
- 紧急阻塞。

每日摘要：

- 普通任务。
- 状态变化。
- 待处理审批。

低频通知：

- 积分到账。
- 内容解锁。
- 排行榜变化。

成员可以按类别设置免打扰时间，但不能关闭安全与强制合规通知。

## 17. 视觉系统

### 17.1 设计方向

概念名称：**工位与作战台**。

- 简单模式：个人今日工作路线。
- 高级模式：管理决策作战台。
- 视觉记忆点：任务路线轨道和跨项目风险证据带。
- 不使用通用 SaaS 卡片网格作为主要结构。

### 17.2 颜色

| Token | 值 | 用途 |
|---|---|---|
| Ink | `#1F2B27` | 正文、标题 |
| Paper | `#F4F6F2` | 主背景 |
| Mint | `#47B7A1` | 进行中、可操作 |
| Mint Deep | `#217766` | 选中、关键数据 |
| Signal | `#D86A45` | 超期、异常、重大事项 |
| Info | `#6F8FBE` | 审批、治理、辅助信息 |

### 17.3 字体

- 中文：`HarmonyOS Sans SC`，回退到 `思源黑体`、`Microsoft YaHei UI`。
- 标题通过字号、字重和留白建立层级。
- 不使用全大写装饰标签。
- 数字使用同一字体的等宽数字特性。

字号层级：

- 32：页面核心数字。
- 24：页面标题。
- 18：区块标题。
- 15：正文。
- 13：次要信息。
- 11：辅助说明。

### 17.4 布局

- 简单模式单列，主按钮保持单手可触达。
- 高级模式采用 38/62 非对称布局。
- 左侧为决策队列，右侧为证据和影响。
- 内容左对齐。
- 行宽默认小于 80 个字符。

### 17.5 动效

- 页面切换和积分到账可以使用动效。
- 列表项不做统一漂浮或逐个淡入。
- 动效必须尊重减少动态效果设置。
- 不用动画掩盖加载或错误。

### 17.6 可访问性

- 移动端和桌面端都支持键盘焦点。
- 不只靠颜色表达状态。
- 正文对比度符合 WCAG AA。
- 重要错误使用明确文字和修复动作。
- 小屏幕优先保证主按钮和验收信息可见。

## 18. 数据与架构

### 18.1 现有技术边界

- 电脑端：Python + PyQt6 + 本地 SQLite。
- 手机端：Capacitor + Web 前端。
- 云端：Supabase Auth、Postgres、RLS 和 RPC。

### 18.2 新增核心实体

- 企业角色模板。
- 角色模板版本。
- 权限定义。
- 成员角色分配。
- 临时兼任职。
- 股东会提案。
- 董事会议案。
- 股份快照。
- 积分池。
- 积分发放记录。
- 知识解锁记录。
- 验收记录。
- 任务依赖和交接。
- 变更申请。
- 工作入口记录。
- 分诊记录。
- 决策队列项。
- 审批实例。
- 审计事件。

### 18.3 服务边界

建议拆分为以下服务模块：

1. Identity & Governance：身份、权限、股份、股东会和董事会。
2. Work Intake：需求入口、分诊、重复检测和外部沟通。
3. Delivery：项目、任务、验收、依赖和变更。
4. Operations：审批、工时、能力、财务和风险。
5. Rewards & Knowledge：积分、奖励和知识解锁。
6. Audit & Notification：审计、通知和事件投递。

模块之间通过稳定 ID 和事件记录关联，不复制业务真值。

### 18.4 数据流

1. 外部或内部工作进入统一入口。
2. 协调员分诊并确定优先级。
3. 转为项目或任务，生成验收标准。
4. 成员执行、记录工时和交付证据。
5. 验收人确认或退回。
6. 系统产生风险、经营和绩效证据。
7. 董事会批准积分池，董事长按依据发放积分。
8. 成员使用积分解锁知识内容。
9. 所有治理和经营动作写入审计。

### 18.5 错误处理

- 网络失败必须显示明确原因和重试入口。
- 权限不足必须说明缺少什么权限。
- 数据版本冲突必须提示刷新并保留用户输入。
- 投票和积分操作必须幂等，重复提交不能重复计票或发分。
- 移动端离线时允许缓存待处理草稿，恢复网络后再校验。
- 关键写入失败不得只在控制台报错。

## 19. 迁移和上线

### 19.1 阶段迁移

- 每个阶段先做数据迁移预览。
- 迁移前自动备份。
- 迁移脚本必须可重复执行。
- 新增字段必须有默认值和兼容策略。
- 旧老板/员工账号继续可登录。
- 首次打开自动初始化企业和董事长身份。

### 19.2 灰度

- 先在企业所有者账号启用阶段一。
- 然后在身份管理员和董事会成员中启用。
- 最后对普通成员开放简单模式。
- 每个阶段保留关闭开关。
- 不因单个新模块故障阻断任务提交和工时记录。

---

## 20. 验收标准

### 20.1 阶段一

- 可复制身份并修改四维权限。
- 身份管理员不能修改自己或授予自己没有的权限。
- 高风险修改进入股东会表决。
- 普通事项和重大事项按确认规则计票。
- 股份调整必须 2/3 股份通过。
- 董事会按一人一票批准积分池。
- 董事长不能给自己发分。
- 简单模式和高级模式按权限显示。
- 所有关键操作有审计记录。

### 20.2 阶段二

- 决策中心默认显示今日必须处理的事项。
- 审批统一进入一个收件箱。
- 项目能看到合同、回款、成本和预计毛利。
- 工时经营维度可统计。
- 能力缺口和风险能下钻到原始记录。
- 绩效依据可查看、可说明、可复核。

### 20.3 阶段三

- 任务未满足验收条件时不能最终完成。
- 依赖延期能计算下游影响。
- 交接需要接收方确认。
- 变更未经批准不能覆盖原计划。
- 验收、返工和变更进入审计。

### 20.4 阶段四

- 外部需求可通过表单、二维码或邮件进入。
- 分诊超时自动升级。
- 重复需求可合并且保留来源。
- 外部状态和内部备注隔离。
- 需求可直接转项目或任务且不断链。

---

## 21. 成功指标

- 任务从分配到验收的平均断链次数下降。
- 需求分诊超时率下降。
- 风险预警被确认和处理的比例上升。
- 审批平均等待时间下降。
- 项目预计毛利偏差缩小。
- 逾期回款发现时间缩短。
- 员工每天打开软件后的第一步操作时间缩短。
- 普通员工对简单模式的理解和完成率上升。
- 积分发放可追溯率达到 100%。
- 敏感内容误入知识星球的次数为零。

## 22. 风险与缓解

| 风险 | 缓解 |
|---|---|
| 功能过多导致简单模式变复杂 | 默认隐藏高级能力，按权限渐进展开 |
| 身份管理员权力过大 | 不能自改、不能超权授予、高风险投票 |
| 大股东自我表决失控 | 允许参与但披露利益关系，重大事项要求 2/3 股份 |
| 游戏化鼓励刷分 | 积分由董事会限额、董事长按证据发放 |
| 统一入口变成新收件箱 | 明确分诊人、SLA 和超时升级 |
| 财务数据泄露 | 高级模式、四维权限、导出审计 |
| 一次性开发风险过高 | 四阶段独立实施和验收 |
| 移动端录入负担增加 | 默认标签、最近使用、快速记录和离线草稿 |

## 23. 实施拆分

本规格覆盖完整目标，不直接对应一次大型开发。实施时按阶段分别编写计划：

1. `阶段一-治理与权限`
2. `阶段二-管理决策`
3. `阶段三-执行追踪`
4. `阶段四-工作入口`

阶段一未通过验收前，不进入阶段二编码。每个阶段都需要独立的设计复核、实施计划、测试和上线检查。

## 24. 设计自检

- 未决项检查：通过，规格内容完整。
- 一致性：股权表决、董事会表决、积分发行和简单/高级模式规则相互一致。
- 范围检查：完整目标已拆成四个独立阶段，避免一次实施过大。
- 歧义检查：普通事项、重大事项、股份调整、积分永久有效、当事人可投票但需披露利益关系均已明确。
- 用户决策：本规格来自多轮 grilling，并以用户确认的推荐方案为准。
